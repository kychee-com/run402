# HPKE interop golden files (D182 acceptance rule 2)

`golden.json` is GENERATED by `../gen_vectors.py` (deterministic; never edit by
hand — regenerate). It carries, for two recipients, every input a sealer or
opener needs and the envelope the Python reference (`pyhpke` 0.6.5, proved
byte-equal against RFC 9180 Appendix A.2.1 at generation time) produced from
them.

**Status: golden INPUTS + reference-sealed envelopes only.** The cross-language
runs the acceptance plan requires have NOT been executed here. They are CI
gates of task 5.1 (the SDK, `@hpke/core`) and task 5.9 (`r402s-verify`, the
rozbb `hpke` crate) — see `../../hpke-second-implementation.md`. Nothing in this
directory claims either implementation has opened anything yet.

## Suite

`r402s-1` = HPKE **Base** mode, KEM `DHKEM(X25519, HKDF-SHA256)` (0x0020), KDF
`HKDF-SHA256` (0x0001), AEAD `ChaCha20-Poly1305` (0x0003). Plaintext = the raw
32-byte `K_repo`; `ct` = 48 bytes (32 + 16 tag); `enc` = the 32-byte ephemeral
X25519 public key.

## Per case (`cases[]`)

| Field | Meaning |
|---|---|
| `recipient.x25519_private_key_hex` / `x25519_public_key_hex` / `fingerprint` | the recipient keypair (TEST material) and `ek_` + first 16 bytes of SHA-256(raw pubkey) |
| `sender.signing_fingerprint` / `ed25519_seed_hex` | the creator's `vk_…` fingerprint (= the envelope's `created_by`) and signing seed, so an implementation can also RE-SIGN an envelope it seals |
| `ephemeral.ikmE_hex` / `skE_hex` / `pkE_hex` | the ephemeral keypair = `DeriveKeyPair(ikmE)` (RFC 9180 §7.1.3); `pkE` == `enc` |
| `info.parts` / `info.hex` | `lp_utf8("r402s/v0/envelope") ‖ lp_utf8("r402s-1") ‖ lp_utf8(lowerhex(SHA-256(recipient raw X25519 pubkey)))` (64 ASCII hex chars, never 32 raw bytes) `‖ lp_utf8(created_by)` (the full `vk_` scalar) — `lp_utf8` = 4-byte big-endian length ‖ UTF-8 bytes, on EVERY component. **Normative per protocol §2 / D188** (the round-38 freeze confirmed these bytes; `../vectors.json` class `hpke-info-near-neighbors` pins the wrong encodings that must FAIL to open) |
| `aad.jcs` / `aad.hex` | `JCS({repo_id, epoch, recipient_kind:"principal", recipient_fingerprint})` — exactly those four members (D188) |
| `plaintext_K_repo_hex` | what a successful open MUST return |
| `sealed_by_reference.enc_hex` / `ct_hex` / `key_envelope` / `stored_bytes_sha256` | the reference seal and the signed, schema-valid `key_envelope` object carrying it |
| `tamper_must_fail[]` | three (enc, ct, aad) triples that MUST fail to open |

## What each implementation must do (task 5.1 SDK / task 5.9 verifier CI)

1. **Open the reference envelopes.** For every case, `open(enc, skR, info, aad, ct)`
   returns `plaintext_K_repo_hex`. Verify the `key_envelope` signature FIRST
   (domain `key_envelope`, strict Ed25519) — the protocol forbids opening an
   unverified envelope.
2. **Reproduce the reference seal if the implementation can inject the
   ephemeral key.** `@hpke/core` accepts an `ekm`/ephemeral key in its sender
   context options and rust-hpke's `setup_sender` takes an RNG (a fixed-seed
   RNG does NOT reproduce `DeriveKeyPair(ikmE)`; use `derive_keypair` + the
   `setup_sender_with_ephemeral`-style test entry where available). When it can:
   `enc`/`ct` MUST equal `sealed_by_reference` byte-for-byte. When it cannot:
   the seal is randomized, and the check is rule 3 only.
3. **Seal for the other.** Each implementation seals `K_repo` for each recipient
   with the case's exact `info`/`aad`, signs the resulting `key_envelope` with
   `sender.ed25519_seed_hex`, and commits the output as
   `sealed_by_hpke_core.json` / `sealed_by_rust_hpke.json` beside this file;
   the OTHER implementation's CI opens them. Both directions green is the
   acceptance condition.
4. **Tamper must fail.** Every `tamper_must_fail[]` entry fails to open in both;
   a flipped byte anywhere in `enc`, `ct`, or any AAD member is a refusal, never
   a garbage plaintext.
5. **Differential third.** `hpke-rs` (CI only) opens the same files; any
   disagreement among the three is a freeze blocker.

`../verify_vectors.py` re-derives every case from the inputs under the Python
reference (seal reproduced via `DeriveKeyPair(ikmE)` + deterministic seal; open;
signature; schema; tampers) — that is the standing proof the golden file is
self-consistent, not a proof of cross-implementation interop.

## Byte continuity (D188, round-39 finding 6) — `../CONTINUITY.json`

The golden bytes an implementation opens are pinned across folds by the
write-once manifest `../CONTINUITY.json`, asserted on every `verify_vectors.py`
run (the generator is re-run into a temp dir and the output byte-compared):

| | sha256 |
|---|---|
| `golden.json` at the D188 fold (rev 38, pre-fold value) | `bf1cb4d4bf5970bfd6ab84f13d739dc7becb1fbf8d42bc3fa61ac0037c703b8d` |
| `golden.json` now (rev 39) | `a02470bab03b77c8fab92ad0698551de7fb77f58c8ef2eec1c1ebfa96d877a51` |
| `golden.json` with `x-r402s-revision` removed — both | `f7c3ff76abbdfb30718e28b86de6250920bb1d52c0db5594a69041d48282b3b5` |

The two whole-file digests differ ONLY in the `x-r402s-revision` member (`38`
→ `39`); the third row is the byte-continuity proof: every key, `enc`, `ct`,
`info`, `aad`, tamper triple, and signed envelope in this file is unchanged
since the fold. A `sealed_by_hpke_core.json` / `sealed_by_rust_hpke.json`
committed against the rev-38 golden file therefore stays valid against the
rev-39 one.
