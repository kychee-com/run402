## 0. Scope, trust boundary, threat properties

**V0-A implements:** lazy six-stage crash-safe vault creation; deploy-implies-capture with push-gated activation bound by capture/activation receipts; encrypted WAL `pack_set`s + signed create-only heads with object receipts; ref transactions; `checkpoint_set` compaction with retention roots (≥90-day unreachable-history contract); two-phase attested prune; the creator's keystore envelope (the only envelope in V0); the recovery receipt; the remote helper; the control-plane API (allocation, sessions, admission, listing, policy management) with a normative authorization matrix and rate/count limits.

**Deferred (§13):** human envelopes/invite (change 3); epoch rotation + transfer (change 4); capsules (change B — **no namespace, prefix, or layout is reserved in V0**; change B chooses its own); selective purge (own change); runner delivery; mirrors; witness anchoring; periodic capture.

**Trust boundary:** the creator's machine + keystore are trusted. `source.run402.com` and the bucket are untrusted for confidentiality — structurally (no key material server-side). The platform separately, custodially holds plaintext source-artifacts of every deploy in its CAS (deploy lane) — the disclosed boundary; that custodial restore is the support path when every principal envelope is lost. **In V0-A, whole-machine or whole-keystore loss is terminal for vault history** (`VAULT_UNRECOVERABLE`) until human envelopes ship; doctor/status state this verbatim. The vault protects source history from host-side loss **while a principal keystore survives** — that is the honest durability sentence.

| Property | Against malicious control plane + bucket |
|---|---|
| Confidentiality | Cryptographic (client-side encryption; no server keys; all server-comparable digests are keyed) |
| Authenticity | Cryptographic for pinned clients; receipt-anchored for recovering clients |
| Freshness | Pin-relative only; genesis receipt gives authenticity, not suffix freshness |
| Availability / durability / retention timing | Operational promises — the host can delete bytes and controls `admitted_at` |
| Activation policy (push gate) | Operational platform invariant, not cryptographic against the platform |

**Client obligations:** compare every finalization receipt against the local expected manifest before signing a head over it; read the admitted head back from storage (verify stored-bytes hash) before reporting a push landed or advancing a pin.

## 1. Notation, parsing, encodings, schemas

- **Canonical JSON** = RFC 8785 (JCS). **Strict parsing:** schema-aware; reject duplicate members, unknown members, non-I-JSON, invalid Unicode, ANY JSON number, noncanonical base64url (every base64url value must round-trip decode→encode byte-for-byte: no padding, length mod 4 ≠ 1, no nonzero trailing bits), non-lowercase hex, noncanonical ids. Machine-readable JSON Schemas for **every JSON object and receipt kind in this document** ship at `test-vectors/r402s-v0/schemas/` (draft set at `docs/strategy/products/gitvault/schemas/`, moved there at freeze) and are normative; the two raw encrypted kinds (`wal_pack`, `checkpoint_pack`) have **binary-frame descriptors** instead of JSON Schemas; **`constants.json` is the SINGLE machine-readable source of every cardinality/size bound** (schema literals and prose tables derive from it and must match — validator-checked); `errors.json` carries the closed error registry; `semantic-constraints.json` inventories every cross-field/cross-object rule the schemas cannot express (equalities, sums, orders, implications — the vector generator and both verifiers enforce them); a standing adversarial validator (`validate.py`) keeps the round-8 schema-valid-but-protocol-invalid instances rejecting. **`apply_plan_canonical/v1` is an EXTERNAL preimage owned by the unified-apply change** — this protocol treats `apply_plan_sha256` as an opaque 32-byte commitment. Task 1.3 refuses freeze if any normative object lacks its schema or descriptor.
- **Hash rules (exactly two):** *stored bytes* of a signed object = JCS of the complete object **including** `signature`; every `*_sha256` naming a signed object is SHA-256 over stored bytes. *Signature preimage* = `"r402s/v0/" + object_kind + "\n" + JCS(object without its single top-level signature)`.
- **Scalars (ABNF):** generation-like fields = exactly 16 lowercase hex. `size_bytes` = `"0" / (%x31-39 *14DIGIT)`. Timestamps = RFC 3339 UTC ms + `Z` (schema-bounded fields, spelled `[0-9]` — never a Unicode-dependent digit class; **implementations MUST semantically parse every timestamp and reject impossible calendar values such as `2026-02-31` or a February 29 outside a leap year** — the pattern and the ABNF bound fields, never month lengths; semantic constraint `timestamp-calendar`, D187); informational unless named server-authoritative. **Exact cryptographic scalar lengths (round-8 B11):** Ed25519 signatures = exactly 86 base64url chars (64 bytes; final char ∈ {A,Q,g,w}); Ed25519/X25519 public keys and the HPKE `enc` = exactly 43 chars (32 bytes; final char in the 16-value padding class); the HPKE-sealed K_repo `ct` = exactly 64 chars (48 bytes) — wrong-length values are schema rejects, never decode-time surprises. Refnames pass the schema pattern PLUS the frozen `git check-ref-format` subset validator (semantic). Ids = `<prefix>_<32 lowercase hex>` (CSPRNG).
- **Identity taxonomy (round-8 A1 — ONE rule per kind):** **ID-ADDRESSED** stored kinds carry `object_id`: `wal_` WAL pack, `refs_` ref state, `rr_` retention roots, `chk_` checkpoint manifest, `ckp_` checkpoint pack, `ccs_` checkpoint claim set, `msc_` maintenance stage claim set, `msp_` maintenance stage page, `mct_` maintenance cycle terminal, `rc_` retention-cutoff ticket, `adm_` admission record, `pi_` prune intent, `pc_` prune completion, `vr_` verifier receipt, `ct_` activation token. **PATH-ADDRESSED, NO `object_id`:** `head` + `vault_genesis` by `(repo_id, generation)` — genesis IS the object at `head/0000000000000000`; `key_envelope` by `(repo_id, epoch, recipient_fingerprint)`; `maintenance_cycle_issuance` at BOTH its idempotency-CAS and tombstone keys; `maintenance_completion_cut` by its admission attempt (`cuts/<admission_object_id>`). **VERSION-ADDRESSED:** the service-key registry. **API/LOCAL MESSAGES, no id:** `allocation`, `capture_receipt`, `recovery_receipt`, `maintenance_open_request`. `src_` names the vault itself. **Non-storage protocol ids:** `mc_` maintenance cycles, `ml_` maintenance leases, `ra_` repair attempts (same 32-hex grammar); service keys are `sk_[0-9a-z-]{4,64}`, unique within the registry.   `transition` is an **embedded descriptor inside `head`**, not a top-level signed kind (it is covered by the head's signature). Genesis is its own kind with its own schema and domain — never a conditional `head`.

A verifier's `restored_object_set_hmac` and the checkpoint manifest's `object_set_hmac` use the SAME `"objectset"` label over the same content — equality is bytewise. Commitment = `HMAC-SHA-256(K_digest(label), JCS(content))`. Every control-plane-signed object carries `service_key_id` naming the exact versioned service key.
- **Ed25519 strict RFC 8032** everywhere (`zip215:false` pinned + acceptance-tested; a ZIP215-only signature is rejected by every component).
- **Keyed digests:** wherever the server compares or stores a digest of plaintext-derived content (restored object sets, ref maps, retention states), the value is `HMAC-SHA-256(K_digest, JCS(content))` with `K_digest = HKDF(K_repo, info=…"digest")` — the server checks equality without gaining a confirmation oracle. Plain hashes of plaintext content never leave the client.
- **Git:** UTF-8 refnames; `sha1` object format (`git_object_format` reserves the lift); 40-hex oids.

## 2. Cryptographic suite (`suite: "r402s-1"`)

| Purpose | Primitive | Implementation |
|---|---|---|
| Signatures | Ed25519 strict | noble-curves, `zip215:false` pinned |
| Envelopes | HPKE base, DHKEM(X25519,HKDF-SHA256), HKDF-SHA256, ChaCha20-Poly1305 (RFC 9180) | primary `@hpke/core`; the **second implementation is selected and reviewed at task 1.0, before vectors** (round-3 plan fix); hand-assembly forbidden; CI runs RFC 9180 + Wycheproof vectors on both |
| Bulk AEAD | XChaCha20-Poly1305 (IETF draft: 32B key, 24B nonce, 16B tag, ct‖tag) | noble-ciphers |
| KDF / Hash | HKDF-SHA-256 / SHA-256 | noble-hashes |

- `k_obj = HKDF(K_repo, salt=∅, info=I, L=32)`; `I` = length-prefixed (`4-byte BE len‖bytes`) `"r402s/v0"`, suite, `repo_id`, epoch, `object_kind`, `object_id`, `"L=32"`. Object ids are single-use key labels; retries read-and-compare, never re-encrypt under an id. (Because `repo_id` is a KDF input, **no ciphertext can be prepared before allocation** — the creation journal §5.2 is ordered accordingly.)
- **Framing:** bytes 0–5 `"R402S0"`, byte 6 suite (0x01), bytes 7–30 nonce, then ct‖tag. AAD = JCS of `{repo_id, object_kind, object_id, epoch, suite, magic:"R402S0", suite_id:"01"}` (frame header authenticated). `ciphertext_sha256` covers the complete framed blob. Max plaintext 256 MiB/object; no unverified streaming release.
- **HPKE (exact bytes — D188):** plaintext = the raw 32-byte K_repo, nothing else. `info = lp_utf8("r402s/v0/envelope") ‖ lp_utf8("r402s-1") ‖ lp_utf8(lowerhex(SHA-256(recipient_x25519_public_key_raw_32))) ‖ lp_utf8(created_by)` — `lp_utf8` is the §1 length prefix (4-byte big-endian byte length ‖ UTF-8 bytes) applied to EVERY component; the third component is the **64 ASCII lowercase-hex characters** of the digest (never the 32 raw digest bytes); `created_by` is the envelope's FULL `vk_`-prefixed scalar exactly as signed (never the bare 32 hex). AAD = JCS of exactly `{repo_id, epoch, recipient_kind:"principal", recipient_fingerprint}` (the four path-identity members, nothing else). Envelope signature verified **before** any open.
- All keys/nonces/ephemerals from the OS CSPRNG.

## 4. Object model

### 4.1 Receipts

Receipts are a **per-kind algebra** (round-8 A1, superseding round-6 H6's two-branch union): every context names its EXACT receipt type — one schema definition per kind, contextual typing schema-enforced. Encrypted kinds (`wal_pack` — the ONLY kind carrying `base_generation`, there REQUIRED — `ref_state`, `retention_roots`, `checkpoint_manifest`, `checkpoint_pack`) are receipted by `{object_id, object_kind, ciphertext_sha256, size_bytes}`; plaintext-structured stored kinds (`checkpoint_claim_set`, `retention_cutoff`, `maintenance_stage_claim_set`, `maintenance_stage_page`) by `{object_id, object_kind, stored_bytes_sha256, size_bytes}`; the **path-addressed `key_envelope` receipt** is `{object_kind, epoch, recipient_fingerprint, stored_bytes_sha256, size_bytes}` — NO `object_id`. `wal_entries[]` accepts only WAL receipts; the head's `ref_state`/`retention_roots` slots only their exact kinds; the checkpoint block only a claim-set receipt and a cutoff-ticket receipt; the claim set only a manifest receipt and pack receipts; genesis only the envelope receipt — a wrong-kind receipt in ANY slot is a schema reject and an admission refusal. **The pruneable union is CLOSED:** `{wal_pack, ref_state, retention_roots, checkpoint_manifest, checkpoint_pack, checkpoint_claim_set, maintenance_stage_claim_set, maintenance_stage_page}` — the two maintenance-stage kinds with a TERMINAL-GATED eligibility (prunable only once their cycle's terminal reaches `TERMINAL_APPLIED`; the terminal + admission record retain everything DR needs) — while admission records, cutoff tickets, key envelopes, verifier receipts, prune intents/completions, and cycle terminal records are NEVER prune candidates in V0 (recovery and DR evidence is structurally unprunable). In every receipt `size_bytes` = the S3 STORED size, server-verified at finalization. The decrypted checkpoint manifest's pack entries carry BOTH representations — `{object_id, plaintext_sha256, plaintext_size_bytes, ciphertext_sha256, size_bytes}` — and **cross-object equality applies only to the shared stored-representation fields** `{object_id, ciphertext_sha256, size_bytes}` between claim set and manifest; totals are distinct (`total_stored_size_bytes` in the claim set; the manifest carries `total_plaintext_size_bytes`). Heads receipt every referenced object; genesis receipts its envelope. A receipted id is permanently bound to those bytes.

### 4.2 `vault_genesis` (own kind, generation 0)

Fields: format/suite, `repo_id`, `org_id`, `project_id`, `allocation_nonce`, `generation:"0000000000000000"`, `epoch` fixed exactly `"0000000000000001"`, `git_object_format:"sha1"`, creator signing + encryption pubkeys, `envelopes:[key-envelope receipt]` (the path-addressed form, §4.1), `writer_key_id`, `created_at`, `signature`. **Genesis carries NO `object_id` and NONE of the head-only fields** (no wal_entries/ref_state/retention_roots/checkpoint, not even as nulls — round-8 B9): it is its own schema, path-addressed as the object AT `head/0000000000000000`. **Genesis key bindings (round-10 A6, validator-computed):** `writer_key_id` = `vk_` + fingerprint(creator_signing_pubkey) = the allocation's `creator_signing_fingerprint`; the envelope receipt's `recipient_fingerprint` = `ek_` + fingerprint(creator_encryption_pubkey) = the allocation's `creator_encryption_fingerprint`; its `epoch` equals the genesis epoch; genesis `repo_id`/`org_id`/`project_id`/`allocation_nonce` equal the ACTIVE allocation's; the stored envelope's `repo_id`/`epoch`/`recipient_fingerprint`/`created_by` equal the genesis values; the recovery receipt carries the same derived pair. A mismatch is a creation-time refusal — an envelope addressed to a foreign fingerprint must never canonize (it would silently void the documented envelope self-restore path). Self-signed (domain `vault_genesis`). The keystore pins `(repo_id → creator pubkey, genesis stored-bytes hash)`; the recovery receipt (§5.4) carries the same pin off-host.

  "epoch":"0000000000000001",

  "checkpoint": null | { "claim_set": { …checkpoint_claim_set receipt… },       // §4.7: transitively claims manifest + every pack

- **V0 epoch continuity (round-9 A4):** every V0 head's `epoch` equals its predecessor's — pinned to `"0000000000000001"` (the genesis epoch) in the V0 schema, since V0 rejects every non-null transition and `rotate_epoch` is post-V0; an epoch may change ONLY across an admitted, ACTIVATED `rotate_epoch` transition (a future protocol revision relaxes the pin together with that activation).
- **Checkpoint conditionals are IFF, schema-enforced (round-8 A5):** `checkpoint` non-null ⇔ `checkpoint_purpose` non-null; `checkpoint_purpose:"repair"` ⇔ `repair` non-null (and a repair head's checkpoint is mandatory); **every checkpoint-bearing V0 head carries `wal_entries:[]`** — content that would ride WAL ships through the checkpoint set instead. **Purpose/resource matrix (normative; a mismatched pair is refused at admission validation):** `checkpoint:null` + `repair:null` → `resource_binding.kind="ordinary_push"`; purpose `ordinary_push` → `ordinary_push` (writer authority); purpose `maintenance_cycle` → `maintenance_cycle` (compact authority; `checkpoint_role` names C1|C2); purpose `repair` → `repair_attempt` + the non-null repair descriptor.
- **Every head carries the complete `retention_roots` receipt** (evolution is verifiable generation-to-generation, §7.1).
- **`transition` is a frozen opaque envelope, and V0 admission REJECTS every non-null transition** with typed `TRANSITION_NOT_ACTIVE` (round-4 H6: recognition must not imply publication authority — otherwise any writer could brick every V0 client). The envelope stays in the parser for forward compatibility: a FUTURE gateway activates a kind only together with its payload schema, semantic validation, a distinct capability, cross-version vectors, and repair behavior; a V0 *client* encountering an admitted transition (published by such a future gateway) fails closed with `UPGRADE_REQUIRED`. Unknown `kind` → reject.
- **`repair` requires the `gitvault.repair` capability at admission** (owner + step-up); invariants: `supersedes_from = base_generation+1`, `supersedes_through = repair generation − 1`, base hash exact; **a repair head MUST carry a freshly accepted, self-contained `checkpoint` claim set** covering the repaired ref state, every repair-preserved superseded tip, and all pre-existing unexpired roots — an owner that cannot construct it gets typed `REPAIR_TARGET_UNPRESERVABLE` instead of publishing an unrestorable rollback (round-4 C4). **Repair-root algebra (exact):** for each superseded generation g in `[supersedes_from, supersedes_through]`, every ref tip of ref_state(g) that is not reachable from the repaired ref state enters the retention-root MAP once per `(ref, oid)` key, with `dropped_at_generation = the repair generation` (renewal semantics). A repair MUST NOT cross any admitted `transition`. **The pending repair fence (round-6 C3 — repair side effects placed safely across the admission-record CAS):** in the `RECORD_PUT_ISSUED` transaction (round-7 A3 — never the earlier claim transaction), repair admission locks the vault row and sets `{pending_repair_admission_id, proposed superseded interval, pending repair_version}` — it does NOT yet mark generations superseded or revoke tokens; while the fence is pending, token mint, token consumption, and prune-start return retryable `REPAIR_FENCE_PENDING`. On observing that this exact admission record WON, one transaction finalizes the interval, increments committed `repair_version` + `gc_epoch`, and revokes every token bound into the interval (`REVOKED_BY_REPAIR`); on observing a DIFFERENT canonical winner, the fence clears with no supersession side effects. Mint inserts, and consumption performs its final supersession + `authorization_epoch` check, under the vault-row lock — and both refuse while a fence is pending. The pending/final fence state is persisted in the admission record for DR. Clients that materialized a superseded generation mark it historical-unusable and jump. Repair rides the **repair resource lane** (§9.3): a bounded reservation covering upload sessions, finalized objects, temporary storage, and admission — not admission alone (round-4 H8); lane objects bind to one repair attempt and are reaped or charged if it is not canonized.

### 4.4 `ref_state`

`{format, object_kind:"ref_state", suite, object_id:"refs_…", repo_id, generation, refs:{<canonical ref>:<40-hex>}, head_target, signature}` — **`head_target` is a discriminated union (round-8 A3):** `{kind:"symref", ref}` where `ref` MUST be a `refs/heads/*` branch (schema-typed `branch_refname`; it MAY name an unborn branch) or `{kind:"detached", oid:"<40-hex>"}`; a detached target's commit is part of required checkpoint coverage AND of the `"refmap"` commitment preimage (the whole ref_state plaintext minus signature) — detached HEAD is representable, covered, and restorable, never a null. Canonical namespace `refs/heads/*`, `refs/tags/*`, `refs/run402/*` (protocol-owned; user pushes refused). Encrypted (`object_kind:"ref_state"`).
**Deploy refs are bounded (round-3 H9):** captures force-move the single ref `refs/run402/deploys/latest` (force-with-lease); the displaced tip enters `retention_roots` in the same transaction, receiving exactly the ≥90-day lane. Per-capture refs do not accumulate. (The durable provenance join is operation ↔ generation, not the ref.)

### 4.5a `retention_cutoff` (`rc_`; control-plane-signed — round-6 C1)

`{format, object_kind:"retention_cutoff", object_id:"rc_…", repo_id, base_head_sha256, cutoff_at (SERVER-AUTHORITATIVE), expires_at, authorization_epoch, service_key_id, signature}` — stored immutably at `retention/<rc_id>.ticket.json`, obtained BEFORE building any checkpoint by ANY principal holding write, compact, or repair authority on the vault (the ticket is a clock attestation; it grants nothing). Validated once, in the admission's IRREVERSIBLE-FENCE transaction — `RECORD_PUT_ISSUED` for P-less admissions, the COMPOSITE fence (§7.2, D154) for P-credit maintenance admissions — and grandfathered thereafter. The head's checkpoint block carries the ticket's plaintext-structured receipt and `cutoff_at`; `retention_roots` carries `cutoff_ticket_sha256` + `cutoff_at`; both verifier receipts bind the ticket hash. A checkpoint that removes NO roots may omit the ticket (the no-removal form). Its stored-bytes hash and `cutoff_at` are bound into the checkpoint's `retention_roots` object and head. **A checkpoint may remove a root only if the root's `effective_admitted_at` + 90 days < `cutoff_at`** — expiry is evaluated against a server time that exists BEFORE signing, never a future storage-commit time. Eligibility is permissive, not mandatory: a delayed admission may make more roots eligible for a LATER checkpoint, never retroactively invalidate this one. Both verifier receipts bind the cutoff-ticket hash.

### 4.5 `retention_roots`

Encrypted; plaintext = `{format, object_kind:"retention_roots", suite, object_id:"rr_…", repo_id, generation, cutoff (the ticket binding, null unless this generation checkpoints with removals), roots:[{ref, oid, dropped_at_generation}] sorted by (dropped_at_generation, ref, oid), no duplicate (ref, oid) keys, signature}` — the authoritative shape is `retention_roots.json`. **Evolution algorithm (normative):** roots(g+1) = roots(g) ∪ {tips dropped or force-displaced by g+1's ref transaction, RENEWING `dropped_at_generation` for an existing `(ref, oid)` key} ∖ {roots whose `effective_admitted_at(dropped_at_generation) + 90d < the bound retention_cutoff ticket's cutoff_at` **when g+1 carries a checkpoint**}; expiry removal happens ONLY at checkpoint-bearing generations, is evaluated ONLY against the pre-signing cutoff ticket, and is permissive (a checkpoint MAY retain eligible roots). **Root identity is a map keyed `(ref, oid)`** (round-6 M12): a later drop of the same key RENEWS its drop generation (full new lane); serialization is the sorted array; the cardinality bound counts map entries. A verifier proves evolution from the prior carrier plus intervening ref states.

### 4.6 `wal_pack` / pack_set

Ordered set per generation; union = `reachable(new tips) ∖ reachable(base tips)` computed in the clean scratch base (checkpoint set + WAL suffix at `base_generation`); every pack independently non-thin, no cross-pack/external delta bases; validation imports the whole set into the exact base then proves connectivity; any single object > 200 MiB → `GIT_OBJECT_TOO_LARGE`; empty set legal. **No aggregate ceiling (round-5 H8):** the client preflights the delta — when it would exceed the direct-WAL budget (`MAX_WAL_RECEIPTS_PER_HEAD` = 64), the push publishes a **checkpoint-bearing head with an EMPTY WAL set** instead: the entire delta ships as a checkpoint set through the claim set (≤4096 packs), at any generation including the first capture. Large first captures are checkpoints by construction, never refusals.

### 4.7 `checkpoint_set` + `checkpoint_claim_set` (round-4 C2: children are claimed transitively)

A checkpoint = one encrypted **`checkpoint_manifest`** + N encrypted **`checkpoint_pack`** chunks + one plaintext-structured, owner-signed **`checkpoint_claim_set`** stored at **`checkpoints/<ccs_id>.claims.json`** (round-5 H6): `{format, object_kind:"checkpoint_claim_set", object_id:"ccs_…", repo_id, manifest_receipt, ordered_pack_receipts[], total_stored_size_bytes, covers_through_generation, writer_key_id, signature}` — only ids, kinds, hashes, and sizes the server already observes (confidentiality-safe; its plaintext exposure is declared in §10). **Receipt hash semantics:** encrypted kinds are receipted by `ciphertext_sha256`; plaintext-structured signed kinds (claim sets, admission records, prune intents/completions, verifier receipts) by **`stored_bytes_sha256`** over their JCS stored bytes. **Cross-field equality is normative:** the head's `covers_through_generation`, the claim set's, and the decrypted manifest's MUST agree exactly, and the claim set's ordered pack ids/hashes/sizes/total MUST equal the manifest's — any mismatch fails acceptance. **The head receipts the claim set; admission validates it and atomically claims the manifest AND every listed pack through it** — no child object is ever left unclaimed for the reaper, and the head's ≤64-receipt cap no longer bounds checkpoint size (a claim set lists up to 4096 pack receipts ≈ 800 GiB at 200 MiB chunks). **Exact total (round-8 A7):** `total_stored_size_bytes = manifest_receipt.size_bytes + Σ ordered_pack_receipts[i].size_bytes` — the claim-set object itself is EXCLUDED, the 800 GiB maximum applies to this exact value, and DR recomputes it from the receipts alone. **Pack limits (reconciled, round-6 H7):** MULTI-OBJECT packs ≤ 200 MiB (target 192 MiB); a SINGLETON pack carrying one maximal Git object may reach the 256 MiB frame limit. **Declared V0 checkpoint maximum — a HARD INVARIANT over required coverage (round-7 A2):** ≤ 4096 packs and ≤ 800 GiB total stored bytes for the coverage a checkpoint must contain — `canonical refs ∪ every unexpired retention root ∪ the HEAD target` (the symref's branch tip when symbolic, the detached commit itself when detached). **Every admission that could enlarge required coverage** (push, ref transaction, root renewal, repair-root addition) preflights the PROJECTED coverage and refuses with `CHECKPOINT_SET_LIMIT_EXCEEDED` BEFORE admission — never only at checkpoint construction: client-side against the plaintext projection; server-side against the conservative stored-bytes bound (current checkpoint `total_stored_size_bytes` + the WAL suffix's stored bytes ≤ the maximum). A vault can therefore never enter an admitted-but-unrepairable or uncompactable state; the §7.2 guarantee refers to full required coverage, not live reachability. The accurate claim is "no direct-receipt aggregate ceiling within the documented V0 checkpoint maximum":

- manifest plaintext: `{format, object_kind:"checkpoint_manifest", suite, object_id:"chk_…", repo_id, covers_through_generation, git_object_format, packs:[{object_id, plaintext_sha256, plaintext_size_bytes, ciphertext_sha256, size_bytes} ordered], total_plaintext_size_bytes, ref_state_hmac, retention_roots_hmac, object_set_hmac, signature}` (authoritative shape: `checkpoint_manifest.json`). **`total_plaintext_size_bytes = Σ packs[i].plaintext_size_bytes`** — the manifest object itself is excluded; it is the plaintext analogue of the claim set's stored-byte total and is NEVER the checkpoint-maximum bound (which binds stored bytes) (round-9 A5) (both representations per entry — equality with the claim set binds ONLY the shared stored fields, round-7 B6) — the three commitments are **keyed digests** (§1) of the covered canonical ref map, unexpired root set, and complete restored object-id set.
- Each pack ≤ 200 MiB plaintext, independently non-thin, no cross-pack deltas; ordered import of all packs into an empty scratch reconstructs the full object set. Empty repository = manifest with zero packs.
- **Coverage rule:** all objects reachable from (a) the covered ref_state's canonical refs, (b) every unexpired retention root, (c) the HEAD target — the symref's branch tip when symbolic, the detached commit oid when detached; an UNBORN symbolic HEAD contributes an explicitly EMPTY coverage component (an empty repository checkpoints with zero packs — never rejected as an unresolved covered branch).
- **Acceptance (producer AND any restorer):** restore from the set alone into an empty scratch (all packs, ordered); every covered ref resolves at its exact oid; `git fsck --no-dangling` full connectivity; recompute and match all three keyed commitments. Failure → `CHECKPOINT_INCOMPLETE` (restorers fall back to WAL replay while it exists).

`{format, suite, repo_id, epoch, recipient_kind:"principal", recipient_fingerprint, enc, ct, created_by, created_at, signature}` (domain `key_envelope`); signature-before-open; readable only by its recipient principal.

### 4.9 `allocation`, `recovery_receipt`

As defined here (signed; domains = their kinds): allocation = control-plane-signed `{repo_id, org_id, project_id, principal_id, creator fingerprints, client_creation_id, allocation_nonce, allocation_generation, status:"active"|"superseded", issued_at, created_at}` (`issued_at` = the authority-time instant of THIS representation, fresh on the superseded republication; `created_at` = immutable creation metadata) — **reclaim supersedes**: a reclaimed allocation's record is republished with `status:"superseded"` and a NEW allocation (new nonce, incremented `allocation_generation`) is issued; a client holding a superseded allocation MUST NOT resume (typed `ALLOCATION_SUPERSEDED`). recovery_receipt = creator-signed `{repo_id, org_id, project_id, genesis_sha256, creator fingerprints}` — integrity data; printed + stored locally + copied to the vault record; a recovery without receipt/pin is labeled unauthenticated salvage.

### 4.10 Control-plane receipts (all control-plane-signed; domains = kinds)

- **`admission_record`** (own id `adm_…`; stored at `admissions/<generation>`): `{object_id ("adm_…"), repo_id, generation, admitted_object_kind ("head"|"vault_genesis"), admitted_stored_bytes (base64url-jcs; decodes to bytes hashing to admitted_sha256), admitted_sha256, prepared_at, capture_binding|null, resource_binding, repair_fence|null, writer_key_id, service_key_id}` — written create-only BEFORE the head/genesis PUT (§5A). **`prepared_at` is the pre-I/O preparation time, NOT the admission time** (round-5 H3): a record may win the CAS long after it was armed. The **effective admission time** — used by retention, capture receipts, and every schedule — is `effective_admitted_at = max(prepared_at, the storage creation time of the winning admission record)` (immutable create-only object metadata, reconstructable in DR). The record also carries the immutable **`resource_binding`** (round-6 H8), a closed union: `{kind:"ordinary_push", cycle_debit|null}` | `{kind:"maintenance_cycle", maintenance_cycle_id, maintenance_lease_id, checkpoint_role:"C1"|"C2", base_head_sha256, prior_checkpoint_claim_set_sha256|null, stage_claim_set_sha256|null (§7.2 — null IFF the expected stage is empty), r1_size_bytes, r2_cap_size_bytes, p_cut_sha256|null (the stored-bytes hash of the role's maintenance_completion_cut object — round-16 A1; null IFF no P is credited), reserved_total_size_bytes, restart_of_maintenance_cycle_id|null, carried_claim_set_sha256|null, carried_reservation_size_bytes|null}` (the three restart fields are non-null TOGETHER, only on a successor C₁ — round-9 A1) | `{kind:"repair_attempt", repair_attempt_id, preempted_maintenance_cycle_id|null, reserved_sessions, reserved_objects, reserved_storage_size_bytes}`. **An immutable record states its ROLE (`checkpoint_role`), never the mutable cycle phase** (round-8 A2). The fence proposal rides the record's own `repair_fence: null | {proposed_supersedes_from, proposed_supersedes_through, pending_repair_version}` — non-null iff the admitted head carries `repair`, equal to its superseded interval; finalized/cleared is derived state, never stored here. **The service signature on the record ATTESTS that the frozen validation of the admission's IRREVERSIBLE fence succeeded** — the composite cut fence for P-credit admissions, `RECORD_PUT_ISSUED` for P-less; there is no separate validation-result field. **`admission_source_bytes_charge`** (ONE accounting function, round-8 A7): the deterministic net-new charge = Σ `size_bytes` over objects FIRST claimed by this admission (each object charged exactly once, at its first claiming admission); `cycle_debit.debited_size_bytes` uses this same function, and `reserved_total_size_bytes` recomputes from `r1_size_bytes`/`r2_cap_size_bytes` via the §7.2 stage-wise formula — upload sessions and finalized-object rows carry the same binding, and DR reconstructs (or conservatively charges) resource state from these immutable records. The record is the admission CAS, the deterministic outbox, and the admission-history log — and per §5A's DR paragraph, deliberately NOT the entire DR story.
- **`capture_receipt`** (API message, no id): `{repo_id, generation, head_sha256, capture_id, apply_plan_sha256|null, snapshot_oid_hmac, admission_record_sha256, issued_at, effective_admitted_at, authorization_epoch}` — returned by admission for any head with a capture_binding. Its `authorization_epoch` is the epoch AT ISSUANCE (what token exchange validates), and `issued_at` is the AUTHORITY-TIME instant (§1) — a receipt reissued after revalidating the canonical admission verifies under the key valid at ITS OWN issuance, so a post-compromise reissue under a new key is accepted and a post-compromise forgery under the old key is rejected (round-9 A2). The keyed snapshot commitment (label `"snapshot_oid"`, §1) lets the server compare a later capture to an operation's journaled snapshot without ever seeing a commit id.
- **`activation_token`** (`ct_`): `{object_id, operation_id, repo_id, generation, head_sha256, capture_id, apply_plan_sha256, snapshot_oid_hmac, issued_at, authorization_epoch, service_key_id}` (epoch = the 32-hex CSPRNG value installed at the last DR gate; compared bytewise; stale → `AUTHORIZATION_EPOCH_STALE`) — minted only when the plan digest is non-null AND the operation row's `capture_id`, canonical plan digest, and snapshot commitment all match; **consumed atomically in the same database transaction as apply activation**, keyed unique on `object_id` (an idempotent success replay for the SAME `operation_id` is a READ of the terminal state, not a new transition; any other operation is refused), and refused (state `REVOKED_BY_REPAIR`) when the bound generation has been superseded by a repair (round-4 C4).
- **`prune_intent` / `prune_completion` / `verifier_receipt`** — §7.3.

## 5. Identity, creation, recovery

### 5.1 Keystore

`~/.config/run402/gitvault/` (`profiles/<wallet>/gitvault/` under a named wallet): `identity.json` (Ed25519 + X25519 private keys), `repos/<repo_id>.json` (K_repo, trust pin, dual pins, last ref transaction), `journal/`. 0700/0600, no-follow creation, permission audit at start, atomic writes, per-repo lock. Partial-loss transitions: repo file lost + identity intact → restore K_repo from own envelope; signing key lost → read-only; stale pin → re-verify from genesis. Whole-keystore loss → `VAULT_UNRECOVERABLE` (§0).

### 5.2 Creation — six durable stages (round-3 H5: ciphertext only after allocation)

```
LOCAL_KEYS_PREPARED   identity + client_creation_id                  (no ciphertext yet —
ALLOCATED             verified allocation: repo_id, nonce, alloc_gen  repo_id is a KDF input)
OBJECTS_PREPARED      exact object ids, nonces, framed bytes (or reproducible source),
                      hashes, sizes — fsynced BEFORE any PUT
OBJECTS_FINALIZED     server receipts, compared to the local manifest
GENESIS_PREPARED      exact genesis stored bytes + hash
ACTIVE                admitted; pin + recovery receipt recorded
```

Allocation is idempotent on `client_creation_id`; owner-reclaimable after 24 h via supersession (§4.9). **Genesis admission is the §5A state machine at generation zero** (admission record at `admissions/0…0`), and it **serializes with reclaim on the allocation row**: reclaim is refused once a generation-zero admission has reached `RECORD_PUT_ISSUED` under the current allocation generation, and a genesis admission is refused once its allocation is superseded — so a stalled creator and a reclaiming owner can never both canonize (round-4 C1's genesis variant). Restart reconciliation per stage; a crash after PUT with `OBJECTS_PREPARED` durable read-and-compares; `VAULT_CREATION_CONFLICT` on foreign genesis; `ALLOCATION_SUPERSEDED` on a reclaimed allocation; destructive retry always refused.

### 5.3 Recovery scope (unchanged, restated)

Terminal-loss sentence per §0. Conformance cases: envelope self-restore; whole-keystore loss truthful; receipt detects substitution; no-receipt = salvage.

### 5.4 Recovery receipt

§4.9; emitted at ACTIVE; not a secret; the more copies the better.

## 5A. Admission, lifecycle, reaping (round-3 C1 fenced)

Ledger tables: `gitvault_objects` — permanent identity rows + lifecycle `FINALIZED_UNCLAIMED → CLAIMED_PENDING(claim_owner) → PUBLISHED → DELETING → DELETED` (**`claim_owner` is TYPED — round-15 A4: `{kind:"admission", admission_object_id}` | `{kind:"prune_intent", prune_intent_object_id}`; intent-owned evidence publishes at `INTENT_STORED` and has NO release edge after the fence**), with the legal non-forward edges (round-5 H5, round-7 A4): `CLAIMED_PENDING → FINALIZED_UNCLAIMED` only when the owning admission (`claim_owner`) is `ABORTED` or `CONFLICTED` (different-winner proof required); `DELETING → PRUNE_AUTHORIZED_PRESENT` on prune preemption; and `PRUNE_AUTHORIZED_PRESENT → DELETING` only under a fresh accepted intent at the current `gc_epoch`; ids never reusable in any state — and `gitvault_head_admissions` (edges: `PREPARED_NO_IO → RECORD_PUT_ISSUED → RECORD_WON → COMMITTED`; `RECORD_PUT_ISSUED → CONFLICTED` — CONFLICTED branches from `RECORD_PUT_ISSUED` ONLY, never from `RECORD_WON`; `PREPARED_NO_IO → ABORTED`, the only abort).

**Admission state machine (round-4 C1 — fenced BEFORE any S3 I/O):**

```
PREPARED_NO_IO → RECORD_PUT_ISSUED → RECORD_WON → COMMITTED
                 RECORD_PUT_ISSUED → CONFLICTED    (a DIFFERENT canonical winner observed — never from RECORD_WON)
PREPARED_NO_IO → ABORTED                           (the only abort)
```

1. Validate: strict parse; strict signature vs the registered writer key; `generation` = newest+1; `prev_sha256` linkage; every receipt (including the checkpoint claim set's transitive children) matches a `FINALIZED_UNCLAIMED` row; capability checks (`gitvault.repair` if `repair` present; `transition` non-null → refuse `TRANSITION_NOT_ACTIVE`; writer otherwise).
2. DB tx #1: claim all objects (`CLAIMED_PENDING`) + admission row `PREPARED_NO_IO`.
3. DB tx #2 — **the admission's IRREVERSIBLE FENCE, in two explicit branches (round-20 A1, totalized rev 22)**:
   - **P-less** (`p_cut_sha256 == null`): persist the **exact signed admission-record stored bytes** (fixing `prepared_at`, the signing key id, and the signature), reserve the generation/rate slot, **validate — atomically, exactly once — every attached authorization** (cutoff-ticket base/service-key/expiry and the current `authorization_epoch`; the pending repair fence, when the head carries `repair`, ARMS in this same transaction; for a maintenance-kind admission this transaction also computes + reserves the expected stage, arms any replacement, consumes the lease, and enters the cycle lane), persist the validation result, and move to **`RECORD_PUT_ISSUED` — irreversible**.
   - **P-credit** (maintenance admissions binding a cut): ALL of the above validation and reservation work — plus fixing the EXACT cut bytes and claiming the cut — already happened in the **COMPOSITE fence transaction** (§7.2), which entered `CUT_PUT_ISSUED` + `CYCLE_ADMISSION_PENDING` together; **this step performs NO validation and acquires NO resource** — it verifies only the forward guard (`cut_subfence == DONE`, stored cut hashes to `p_cut_sha256`) and moves to `RECORD_PUT_ISSUED` as mechanical no-fail replay of the already-persisted exact record bytes. **A FALSE forward guard — the stored cut absent, or its stored-bytes SHA-256 ≠ `p_cut_sha256` — is an EXTERNAL storage-integrity fault, never an admission outcome (D190):** the gateway returns the typed, non-retryable `CUT_STORAGE_INTEGRITY_FAILURE`, issues NO record PUT, and changes NO admission, lane, claim, stage-reservation, cut-ownership, replacement-arm, rate-slot, lease, or authority state — the attempt id and its per-attempt cut key stay burned — and the vault stays fail-closed for this attempt until the exact journaled cut bytes are restored at that key (the guard then holds and the mechanical path resumes) or a superseding recovery decision is applied by an operator. It is not `ABORTED`, not `CONFLICTED`, not `DR_ORPHANED_PRE_RECORD`: none of those release proofs exists. `PREPARED_NO_IO` still means no I/O before an irreversible fence — the composite fence IS that fence for P-credit. **After this transition, current epoch and expiry are NEVER re-evaluated for this admission** (round-7 A3): a canonical winner is historically valid, DR reconciles armed admissions under this grandfathering rule, and historical verification checks signatures and service-key validity at the frozen admission point — never equality with the current epoch. Only `PREPARED_NO_IO` with `cut_subfence == NONE` may ever abort and release claims (a P-credit admission past its composite fence never aborts — every check that could refuse already ran inside it; aborted work must obtain fresh authorization).
4. Create-only PUT of `admissions/<generation>` — the CAS. Win → `RECORD_WON`. On ANY uncertainty, **retry the identical PUT forever**; claims are released only after **observing a DIFFERENT canonical admission record at this generation** (the competing winner permanently fences our still-pending conditional PUT) → `CONFLICTED`, `409 HEAD_CAS_CONFLICT` + winner (client re-verifies from storage).
5. Create-only PUT of `head/<generation>` (deterministic — no competitor exists past step 4; the record holds the exact head bytes). Retry identically on uncertainty → `COMMITTED`, objects `PUBLISHED`.
6. Reconciler: `PREPARED_NO_IO` past timeout AND `cut_subfence == NONE` → abort + release (a P-credit admission past its cut sub-fence never aborts — the reconciler drives `CUT_PUT_ISSUED → CUT_STORED` instead). `RECORD_PUT_ISSUED` → retry the record PUT until won or a different winner is observed. `RECORD_WON` → drive the head PUT to completion, never abort. Idempotent byte-identical replay at any step → success.

**Reaper:** only `FINALIZED_UNCLAIMED` objects whose session lease has expired, via `DELETING` (conditional) then delete then `DELETED`. Structurally cannot touch claimed/published objects.

**Ledger disaster recovery (round-4 C5 — the admissions log is the admission history, NOT the whole DR story):** on any DB/bucket divergence (e.g. point-in-time restore), the gateway reconstructs published-object rows and admission times from admission records + head receipts (including claim-set children). **Tombstones re-derive from ACCEPTED prune intents ∪ completions** — an accepted `prune_intent` permanently burns every candidate object id regardless of whether its completion exists, and DR reconciles actual object presence against intents before any upload or admission resumes (closes the partial-prune id-reuse hole). **Policy recovers fail-closed: any uncertain or discontinuous `gitvault_policy` history recovers as `required`** (an owner can explicitly re-grandfather afterwards); `policy_version` is a monotonic column serializing policy changes with activation (§6.5). Allocation supersession before genesis is folded into the generation-zero admission fence (§5.2). Prune remains refused wherever an admission time cannot be proven. **A scan-visible `maintenance_completion_cut` with no recovered sub-fence journal and no canonical record binding it** (post-quiescence, second scan complete) **is `DR_ORPHANED_PRE_RECORD`**: an inert lifecycle row is reconstructed, claims and reservations release, and the reaper takes it — the cut carries no record bytes, so orphan adjudication (never record-PUT resumption) is the total answer; a binding canonical record adopts it, and a different generation winner reconstructs `CONFLICTED`. **DR classifies journal presence FIRST (D190):** when the composite/record journal is recovered (`present`), the sole legal recovery action is byte-identical resume of the persisted live relation and NO bucket-reconstruction arm may execute; only when the journal is `absent_after_quiescence` does reconstruction classify the canonical record, with exactly one result — `none` → `DR_ORPHANED_PRE_RECORD`, `binds_exact_cut` → adopt to `COMMITTED`, `different_winner` → `CONFLICTED`. When `DR_ORPHANED_PRE_RECORD` applies to a successor C₁ whose replacement arm is `PENDING`, the SAME reconstruction transaction clears that arm to `CLEARED`: the predecessor remains the sole open cycle, and the transaction publishes no predecessor terminal, installs no successor, and transfers no carried reservation.

**DR quiescence gate (round-5 C1 — normative; DB restore alone is NEVER sufficient):** before resuming after any ledger restore/failover, the platform MUST (1) fence and terminate EVERY source-mutating and token-touching actor — gateway API workers, token-mint and apply-commit/apply-activation paths, policy management, prune workers, the reaper, and the reconciler, including their database sessions — and revoke their credentials; (2) wait the maximum external request+retry lifetime; (3) perform two strong-consistency bucket scans separated by that interval (so late-visible PUTs/DELETEs are caught); (4) invalidate every pre-genesis allocation (fresh allocation generation required); (5) mint a fresh random **`authorization_epoch`** that invalidates every outstanding activation token — tokens carry the epoch, and mint/consume/repair checks all verify it (`AUTHORIZATION_EPOCH_STALE`); (6) force uncertain policies to `required` even where the recovered DB has no vault row but the bucket holds a genesis; (7) resume uploads, admissions, prune, and activation only after reconciliation completes. The late-visible generation-zero admission record and the late prune DELETE are explicit staging fault tests, not corollaries. Staging tests cover PITR-behind-bucket divergence, partial-prune restore, allocation-reclaim rollback resume, and policy rollback.

**Count/abuse limits (round-3 H16):** per-principal/per-project caps on upload sessions per hour, finalized objects per day, direct WAL receipts per head (`MAX_WAL_RECEIPTS_PER_HEAD` = 64 — the budget counts `wal_entries` ONLY; the fixed structural receipts — ref state, retention roots, claim set, cutoff ticket — are mandatory, independently bounded, and never debit it), tombstones per day; a minimum accounting charge of 64 KiB per object; reaper/reconciler queries partitioned so work is never proportional to historical tombstones.

## 6. Publication

### 6.1 Ref transactions

`{updates:[{ref, expected_old_oid|null, new_oid|null, force}]}` — non-force branch updates MUST be fast-forward AND match expected-old; `force:true` skips ancestry but STILL requires expected-old (force-with-lease is the only force; null expected-old only for creation); tags immutable without force; deletes require expected-old; multi-ref atomic; **updates MUST name pairwise-distinct refs — a transaction with two updates for the same ref is refused before evaluation, never last-wins** (round-9 A4); conflict-retry re-applies to the winner's map; `REF_EXPECTED_OLD_MISMATCH` per failing update, never a silent revert. Dropped/displaced tips enter `retention_roots` in the same generation.

### 6.2 Push protocol

Discover (§6.3) → verify to newest → decrypt ref_state + retention_roots → evaluate transaction → build pack_set in scratch → upload session (compare receipts to manifest) → build ref_state(g+1) + retention_roots(g+1) → build + sign head → admission (§5A) → on 409 refetch winner from storage, re-apply, retry → read back the admitted head, verify stored-bytes hash → advance authenticated pin; after materialization advance materialized pin.

### 6.3 Discovery — listing only

`GET /gitvault/v1/vaults/:vault_id/heads?after_generation=<required verification anchor>&cursor=<optional opaque continuation>&limit=` (≤1000/page, bucket-derived, ascending, with stored-bytes hashes; response `{format, repo_id, after_generation, heads[], has_more, next_cursor, total}` — `after_generation` is the REQUIRED client-supplied verification pin (a semantic input, never a paging knob; echoed in the response and CONSTANT across one page sequence), `cursor` the optional opaque continuation (omitted on the first request, then the prior page's `next_cursor` echoed UNCHANGED — store and echo, never parse), `next_cursor` the opaque platform-standard continuation (`has_more == false ⇒ next_cursor == null`; `has_more == true ⇒ a non-null opaque next_cursor`), `has_more` truthful on every page, `total` null unless already known; a missing or malformed `after_generation` or `limit` is a request-validation refusal, a malformed, tampered, or stale `cursor` (one not minted for this vault under this `after_generation`) is typed `INVALID_CURSOR` — never a silent restart from the pin; `next_after_generation` is FORBIDDEN (schema `additionalProperties: false`; request contract `heads_listing_request.json`, response `heads_listing_page.json`) — D184 as completed by D186). **Always list from `pinned_generation`** — there is no hint (round-3 H10); verify every link upward. Budget: > 100 000 heads of pending verification → typed `VERIFICATION_BUDGET_EXCEEDED`, never silent acceptance of a lower head. Malformed listing keys and gaps → `CHAIN_BROKEN` (fail closed). Freshness limit per §0.

### 6.4 Dual pins

`highest_authenticated` (chain-verified; regression below it = `GENERATION_REGRESSION`, no publish) and `highest_materialized` (decrypted + applied; the only push base). Authenticated-but-unusable → `CHAIN_UNUSABLE`: read-only at materialized + repair path. An unvalidatable `transition` → `UPGRADE_REQUIRED` (read-only past it, no publish). Documented limits: old keystore backup = old pin; receipt gives no freshness; no pin protects availability.

### 6.5 Deploy-implies-capture (round-3 C3 split)

- `gitvault_policy ∈ {required, grandfathered}` on the project; `required` from allocation. Policy changes ONLY via `gitvault.policy.manage` (owner + step-up, audited, reason, doctor-persistent warning while grandfathered, defined return to `required`). **`policy_version` (monotonic) serializes policy with activation**: the activation transaction re-reads the policy row and its version — a return-to-`required` can never race an unvaulted activation whose authorization was decided outside the transaction (round-4 H9). DR recovers uncertain policy as `required` (§5A).
- Fresh `capture_id` before both lanes; snapshot commit first; **the deploy lane VERIFIES snapshot correspondence rather than isolating the build** (D192): the client digests the captured file set at capture, re-derives that digest after artifacts are collected and before the apply plan is committed, and on any difference REFUSES the deploy by name with `SNAPSHOT_MOVED_DURING_DEPLOY`, naming the changed paths and committing no plan. Artifacts MAY be collected from the working tree; the claim covers the CAPTURED SET only (tracked plus untracked-but-not-ignored — a build that rewrites ignored outputs between capture and commit is not a move), and the guarantee is that the captured source did not change while the artifacts were produced, NOT that the artifacts are a reproducible function of it. `SNAPSHOT_MOVED_DURING_DEPLOY` is CLIENT-LOCAL and deliberately absent from the §11 registry — the refusal happens before any plan is committed, so the code never crosses the wire — and is documented in the client's own error surface instead.
- The push's head carries `capture_binding {capture_id, apply_plan_sha256|null, snapshot_oid_hmac}` — the digest is null when no canonical apply plan exists yet (build failed pre-plan): capture-the-attempt survives; no token is mintable from a null digest. **Canonical plan bytes are a frozen, versioned schema** (`apply_plan_canonical/v1`: the unified-apply canonical manifest form — entries sorted by (kind, key/path) — serialized as JCS with a version tag; committed as a schema + byte/hash vectors) — never a prose reference (round-4 H9). **That schema and its fixtures are OWNED AND PUBLISHED by the unified-apply change** (external to the r402s schema set); r402s vectors consume the published fixtures by exact artifact hash, and the vault layer treats the digest as an opaque 32-byte commitment.
- Admission returns a `capture_receipt`; when the plan digest is present the client exchanges it for an **`activation_token`** — the mint verifies the operation row's `capture_id`, canonical plan digest, AND snapshot commitment — consumed atomically + idempotently at apply activation (§4.10), refused when superseded by repair.
- **Override**: `--allow-unvaulted` requires `gitvault.override_unvaulted` (owner + step-up or explicit emergency grant). Journal contents: `{repo_id, operation_id, capture_id, apply_plan_sha256, snapshot ref+oid, snapshot_oid_hmac, publication state}`. Completion: a later `capture_receipt` matching **all of** {repo, operation's capture_id, plan digest, snapshot_oid_hmac, head hash} is presented to `POST …/override-completions`; equality on every field or no clear. Advisory persists until then.
- **Cardinality bounds (round-4 H10, refused pre-acceptance with `REF_STATE_LIMIT_EXCEEDED`):** ≤ 10 000 canonical refs; ≤ 1 000 updates per ref transaction; ≤ 50 000 retention-root entries (and the serialized ref_state/retention_roots objects ≤ 32 MiB each); ≤ 10 000 repair-added roots. A transaction whose resulting state would be unrepresentable is refused before acceptance — the vault can never wedge itself into an unpublishable next state.
- **Outcome enum (closed, five):** `DEPLOYED_AND_VAULTED`, `DEPLOY_BLOCKED_PUSH_FAILED`, `DEPLOY_FAILED_VAULTED`, `DEPLOY_FAILED_UNVAULTED`, `DEPLOYED_UNVAULTED_OVERRIDE`. `gitvault_commit` printed client-side always; commit ids never reach the platform.

### 6.6 Snapshot + hardened git (round-3 H11)

Snapshot policy: clean → `HEAD`; dirty → synthetic commit of tracked + untracked-not-ignored paths; unborn HEAD → parentless; unmerged index → `SNAPSHOT_CONFLICTED_INDEX` (fails deploy); detached HEAD supported; linked worktrees refused by name. **Ignore authority (frozen, with exact discovery — round-5 H9):** repository `.gitignore` + `.git/info/exclude` + the user's global excludes file, all **read directly as data**. Discovery of the global excludes path (deterministic, round-6 M11): read `$XDG_CONFIG_HOME/git/config` (default `~/.config/git/config`) THEN `~/.gitconfig`, as data with a frozen config subset — sections/keys, quoted values per git-config quoting, duplicate keys LAST-VALUE-WINS in read order (so `~/.gitconfig` overrides), `~/` and `$HOME` expansion only (any other relative or env-dependent path → refuse by name); `include`/`includeIf` constructs → refuse the capture by name; an unreadable CONFIG file (not only the excludes file) → refuse by name; when no `core.excludesFile` is set, the default is `$XDG_CONFIG_HOME/git/ignore` falling back to `~/.config/git/ignore`; an existing-but-unreadable excludes file refuses the capture — never a silently widened snapshot. Vectors: dual-file conflict, include refusal, quoted paths, unreadable config, unset XDG. **Snapshot object creation NEVER invokes filters for any path, tracked or untracked** — raw bytes are hashed via plumbing with filters structurally disabled, and an acceptance test asserts no configured filter/hook process ever starts. Filter detection (for the refusal) applies to every included path. All git invocations: argv-only, cleared `GIT_*`, `GIT_CONFIG_NOSYSTEM`, no user config, empty hooksPath, alternates/grafts/replace/fsmonitor/includes neutralized; version range probed.

## 7. Retention, compaction, prune

### 7.1 Contract — **at least 90 days**

Unreachable history (dropped/force-displaced tips) is recoverable for **at least 90 days** from the drop's **`effective_admitted_at`** (§4.10 — storage-commit time, never the pre-I/O `prepared_at`; a delayed record PUT extends the lane, never shortens it; the delayed-PUT case is a virtual-clock vector). Roots expire from `retention_roots` only at the first checkpoint-bearing generation after expiry (§4.5); physical bytes disappear only at the first successful prune after that. History MAY remain longer; conformance tests "recoverable at day 89" (guaranteed) and "a post-expiry checkpoint no longer covers the root, and the subsequent prune removes it" — the calendar-exact day-91 refusal test is replaced by this schedule-relative pair. Retention timing is an operational promise (§0 table).

### 7.2 Compaction (`run402 gitvault compact`, manual)

Materialize newest g → repack → build the `checkpoint_set` + claim set (§4.7) → acceptance self-check → upload + finalize → publish head g+1 carrying the claim-set receipt, a fresh ref_state, and the evolved retention_roots. **Checkpoint admission classes (round-6 C2, closed in round-7 — every checkpoint-bearing head declares `checkpoint_purpose ∈ {ordinary_push, maintenance_cycle, repair}`):**
- **`ordinary_push`** — authorized by `gitvault.writer`; ALL net-new stored bytes use ordinary org quota (no bootstrap or maintenance overage — a 20 GiB first capture must fit the org's quota, honestly); may use the claim-set path purely to escape the receipt-count ceiling.
- **`maintenance_cycle`** — requires `gitvault.compact` (or the repair lane); carries a durable **`maintenance_cycle_id`** with the CLOSED machine `PREPARED → C1_ADMITTED → INTERMEDIATE_PRUNED → C2_ADMITTED → COMPLETED` plus terminals `ABORTED_BEFORE_C1`, `RESTART_REQUIRED_AFTER_C1` (a TERMINAL, reachable from `C1_ADMITTED` AND from `INTERMEDIATE_PRUNED` when ordinary growth exhausts remaining `R2_cap`; a successor cycle references the admitted C₁ as its base and the C₁ reservation carries forward), `EXPIRED_STALLED`, and `PREEMPTED_BY_REPAIR` (the reservation release and the conversion of C₁'s already-stored bytes to ordinary charged storage occur ONLY in that terminal's `TERMINAL_APPLIED` transaction — conservative and DR-derivable), serialized at the ORG level. `C2_ADMITTED → COMPLETED` requires the COMPLETION-CONFIRMED prune of the superseded material; every `P_before_*` counts only completion-confirmed deletions, never mere eligibility. **Ordinary admissions while a cycle is open carry an immutable `cycle_debit`** in their resource_binding, debited against remaining `R2_cap`; beyond it the ordinary admission is refused with `MAINTENANCE_CYCLE_RESTART_REQUIRED` (round-7 A1). **The committed stage is a STORED, PAGED, COMPLETE object (round-10 A1 + round-11 A1/A2):** each C₁/C₂ admission binds — by UNKEYED stored-bytes hash in its `resource_binding.stage_claim_set_sha256`, so the GATEWAY can verify it, including after DR — an owner-signed **`maintenance_stage_claim_set`** ROOT (`msc_`, at `maintenance/<msc_id>.stage.json`): `{maintenance_cycle_id, maintenance_prune_role, candidate_count, batch_count, stage_candidate_stored_size_bytes, stage_metadata_stored_size_bytes, page_receipts:[≤4096 ordered receipts of owner-signed maintenance_stage_page objects]}` — each **page** (`msp_`) holds ≤10 000 complete pruneable receipts, globally sorted by object_id across the page sequence; **page i IS batch i under CANONICAL PACKING** (every page except the final holds EXACTLY 10 000 candidates; `batch_count = page_count = ⌈candidate_count/10000⌉`; `candidate_count` = Σ page lengths; `stage_candidate_stored_size_bytes` = Σ candidate `size_bytes` — **D_stage, deletion/accounting EVIDENCE only, NEVER re-charged** (candidates were charged at their first claim; round-13 A5) — and `stage_metadata_stored_size_bytes` = the root's + every page's stored bytes — **A_stage, the role's NET-NEW charge**, entering `admission_source_bytes_charge`; the peak formula's terms are DEFINED as **`R1 := admission_source_bytes_charge(C₁)`** — the exact sum over every object FIRST claimed by the C₁ admission (checkpoint children, the claim-set object, the fresh carriers, the stage root and pages; no alternate decomposition) — and `R2_cap` := the maximum permitted `admission_source_bytes_charge(C₂)` under the defined growth envelope). The admission validates and atomically CLAIMS the root AND every page transitively (claim-set precedent). **Capacity is a PROSPECTIVE invariant (round-12 A5, the coverage-preflight precedent):** every admission that could enlarge a future expected stage preflights BOTH the projected `candidate_count ≤ MAX_STAGE_CANDIDATES` (40 960 000 = 4096 × 10 000) AND the projected `stage_candidate_stored_size_bytes ≤ MAX_STAGE_CANDIDATE_STORED_BYTES` (10¹⁴ — every aggregate fits the 15-digit `size_bytes` grammar) and refuses `MAINTENANCE_STAGE_LIMIT_EXCEEDED` — an admitted vault's complete stage is always representable. **Stage metadata lifecycle:** once the cycle's terminal reaches `TERMINAL_APPLIED`, the root and pages become ordinary PRUNEABLE objects (terminal-gated eligibility, §4.1) — no permanently charged, unpruneable evidence. **COMPLETENESS, reconciled with the prune-root algebra (round-11 A1 + round-12 A1):** the concatenated candidates MUST equal **`expected_stage(role, freeze point)`** BYTE-FOR-BYTE — equality over the ENTIRE typed receipt, not just ids — where the UNIVERSE is a deduplicated map keyed `object_id` of every present, unburned pruneable stored object (checkpoint claim-set children expanded transitively) receipted along the canonical predecessor chain PLUS the exact proposed checkpoint head bytes at the fence, EXCLUDING candidates owned by any intent past its own pre-I/O fence; and the PROTECTED set uses the SAME algebra as §7.3's GC roots, over **checkpoint RECOVERY BUNDLES (round-13 A1)**: `RB(K) = K's claim set + manifest + all packs + K's covers_through head's ref_state + retention_roots` — protecting packs without their carriers would keep bytes while destroying the ability to materialize and verify the rollback. `protected_after_C1 = RB(K₁) ∪ RB(K₀) ∪ every receipt of later heads`; **`expected_intermediate_stage = universe ∖ protected_after_C1`** — so K₀'s ENTIRE bundle survives the intermediate stage; `protected_after_C2 = RB(K₂) ∪ RB(K₁) ∪ later receipts`, so **RB(K₀) becomes eligible only in the FINAL stage**. Role mapping is BICONDITIONAL: `checkpoint_role C1 ⇔ maintenance_prune_role intermediate`, `C2 ⇔ final`. A strict-subset, strict-superset, wrong-role, or false-empty stage is REFUSED at the C₁/C₂ admission fence; `stage_claim_set_sha256` is null IFF `expected_stage` is empty — an empty stage advances immediately. **RESERVATION (round-11 A2, linearized round-12 A3):** ordinary-prune candidate OWNERSHIP moves to the intent's OWN pre-I/O fence — the `INTENT_PUT_ISSUED` transaction durably marks every candidate `DELETING`/intent-owned and burns its id BEFORE any S3 I/O (admission's proven pattern; the intent key is unique, so the identical PUT retried forever always eventually wins and a stored-but-unaccepted intent is impossible by construction). The C₁/C₂ admission's IRREVERSIBLE-FENCE transaction (the COMPOSITE fence for P-credit, `RECORD_PUT_ISSUED` for P-less — D154) reserves every stage candidate id for `(cycle, role)`; an ordinary prune intent naming a reserved candidate is refused with `STAGE_CANDIDATE_RESERVED`; `expected_stage` excludes fence-owned candidates, so no in-flight-PUT window exists in either direction. **Reservations release, each at its linearization point:** a CONFLICTED C₁/C₂ admission (different-winner proof) and a replacement CLEAR release in their named NONTERMINAL transactions; `ABORTED_BEFORE_C1`, replacement install (the successor's reservation REPLACES the predecessor's), repair preemption, expiry, and completion release ONLY inside that terminal's `TERMINAL_STORED → TERMINAL_APPLIED` transaction; DR reconstructs reservations only from canonical winners or fenced pending operations with recoverable bytes. `prune_intent_core` and `prune_completion` carry `maintenance_cycle_id`, `maintenance_prune_role ∈ {intermediate, final}`, `stage_claim_set_sha256`, and `batch_index`/`batch_count` — ALL non-null (completion mirroring the intent exactly) for cycle-advancing prunes, ALL null for ordinary prunes; the gateway verifies each batch's delete set equals **page i verbatim**. **Stage advancement:** `INTERMEDIATE_PRUNED` (and `COMPLETED`, via the `final` role) derives ONLY when every page/batch `1..batch_count` of the bound stage has an accepted `completed` completion — a partial or stale batch never advances; a cycle batch terminating `superseded_*` coincides with cycle preemption (the epoch bump came from the repair fence) — there is NO present-subset retry inside an open cycle (that rule is for ordinary prunes); a non-stale transient failure resumes the SAME intent. The C₁/C₂ admission records carry the immutable `checkpoint_role:"C1"|"C2"`; the mutable phase is DERIVED, never stored: `C1_ADMITTED` = the role-C1 record; `INTERMEDIATE_PRUNED` = the C₁-bound stage's complete batch set; `C2_ADMITTED` = the role-C2 record; `COMPLETED` = the C₂-bound stage's complete batch set. **Restart is an ATOMIC REPLACEMENT FENCE (round-10 A2):** a REFUSED ordinary admission leaves no record and terminalizes NOTHING; a successor C₁ (with `restart_of_maintenance_cycle_id` naming the CURRENT open cycle + `carried_claim_set_sha256` + `carried_reservation_size_bytes`, C1-only — schema-enforced) arms a PENDING replacement in its IRREVERSIBLE-FENCE transaction (COMPOSITE when the successor C₁ credits P, `RECORD_PUT_ISSUED` otherwise — D154) under the org-slot lock; the predecessor remains the SOLE open cycle while pending, and cycle progression on either returns retryable `CYCLE_REPLACEMENT_PENDING`; on the successor record observed WON, the predecessor's RESTART terminal publishes through the terminal machine, and at ITS `TERMINAL_STORED → TERMINAL_APPLIED` step ONE idempotent transaction terminalizes the predecessor `RESTART_REQUIRED_AFTER_C1`, transfers the carried reservation, and installs the successor as the sole open cycle — **INSTALLED coincides with the predecessor terminal's APPLIED, never with the admission win alone (round-13 A2)**; on a different canonical winner the fence clears and the predecessor stays open; the orphan adjudication of a successor's attempt (`DR_ORPHANED_PRE_RECORD`, D190) clears it the same way, in the reconstruction transaction, with no predecessor terminal, no install, and no carried-reservation transfer. A repair's binding names `preempted_maintenance_cycle_id`. **Progress clock + the CYCLE-EVENT LANE (round-11 A3 + round-12 A4):** all cycle events — batch-completion acceptance, **EVERY maintenance-kind admission fence** (round-13 A3, start moved round-20 A1: `CYCLE_ADMISSION_PENDING` begins IN the admission's irreversible-fence transaction — the composite fence for P-credit, `RECORD_PUT_ISSUED` for P-less — and holds until the record CAS resolves; while pending, expiry, owner abort, the repair arm, the replacement arm (except the replacement's OWN successor fence), and terminal publication all DEFER; a winning ORDINARY C₁/C₂ record advances the phase; a winning SUCCESSOR record only records RESTART_SOURCE_PROVED — transfer/install/terminalize occur solely at the predecessor terminal's `TERMINAL_APPLIED`; a DIFFERENT winner releases that admission's stage reservations), replacement arm/finalize/clear, **the repair-fence ARM** (validated against the actual open cycle via the binding's `preempted_maintenance_cycle_id`, with no replacement or maintenance-admission fence pending, BEFORE the repair record PUT), repair preemption, terminal publication, and `EXPIRED_STALLED` terminalization — serialize in ONE linearized lane under the org-slot lock. **Maintenance-cycle ids are SERVICE-ISSUED at cycle open, org-global, and permanently tombstoned** — a create-only, service-signed **`maintenance_cycle_issuance`** object is stored — with exact signed bytes persisted first — at TWO keys IN ORDER (round-16 A3): FIRST the **idempotency CAS** `maintenance/open-ids/<sha256(org_id‖repo_id‖client_open_id)>.json` (concurrent retries race ONE create-only key; the winner is authoritative and every retry reads it and returns ITS `maintenance_cycle_id`; the same key presented with different bindings refuses `CLIENT_OPEN_ID_CONFLICT`), THEN the identical-bytes **tombstone index** `maintenance/issued/<maintenance_cycle_id>.json`, and only then the response. The object carries **`open_binding_sha256`** — SHA-256 over the domain-separated, length-prefixed preimage `"r402s/v0/open-binding" ‖ lp(client_open_id) ‖ lp(base_head_sha256) ‖ lp_opt(prior_checkpoint_claim_set_sha256) ‖ lp(requested_r2_cap_size_bytes)` (the canonical cycle-open request, its own schema; **`lp_opt(null) = 0x00` and `lp_opt(x) = 0x01 ‖ lp(x)`** — the tagged null encoding, exact) — a retry compares it byte-for-byte with the winner's BEFORE returning, so `CLIENT_OPEN_ID_CONFLICT` is executable from stored evidence alone, including after PITR; the open-ids key preimage is likewise exact: `SHA-256("r402s/v0/open-id" ‖ lp(org_id) ‖ lp(repo_id) ‖ lp(client_open_id))`. **Three predicates, all DR-derivable (round-17 A2): `ISSUED(c)`** = the open-ids issuance object exists (mirror driven pre-response); **`INSTALLED(c)`** = an ordinary C₁ canonical record (`restart_of == null`) exists OR a predecessor RESTART terminal reached `TERMINAL_APPLIED` naming c; **`OPEN(c)`** = `INSTALLED(c)` AND c's own terminal has NOT reached `TERMINAL_APPLIED` — a C₁ record alone NEVER proves OPEN (historical records outlive terminals); the org slot and lease bind to the OPEN cycle via the binding's `maintenance_lease_id`. An ISSUED-but-never-INSTALLED id simply remains tombstoned. **The cycle-open RESPONSE is the byte-identical signed issuance object** (no separate response schema), and **the request BINDS to installation (round-18 A1)**: at the C₁ fence the gateway loads `issued/<cycle_id>`, recomputes the binding from the C₁ resource binding's `base_head_sha256` / `prior_checkpoint_claim_set_sha256` / `r2_cap_size_bytes` — the admitted cap MUST equal the requested cap in V0, no negotiation — and REFUSES on inequality with the signed issuance digest, so an id issued for request A can never install request B. The DR double scan re-adopts BOTH keys, so a returned-but-unmaterialized id survives PITR and tombstones reconstruct from issuance ∪ materialized records; reuse is refused before any lease, stage object, or admission crosses a fence (a terminal path and an event-seq namespace are never reused). **Arm precedence:** a pending replacement DEFERS the repair arm until installed/cleared, and a pending repair fence defers the replacement arm — the two fences are mutually exclusive, so a replacement and a repair preemption can never both become canonical against different vaults of one org. `last_cycle_progress_at = max(effective_admitted_at of admissions with resource_binding.kind = "maintenance_cycle" for THIS cycle — ordinary admissions carrying only a cycle_debit are NOT progress, completed_at of every ACCEPTED cycle-tagged completed batch completion)` — EACH accepted completed batch resets it. `EXPIRED_STALLED` terminalizes ONLY in the lane, and ONLY when `now ≥ last_cycle_progress_at + 7 days` AND no replacement fence is pending AND no cycle-tagged intent for this cycle is accepted without an accepted completion AND no completion write is past its pre-I/O fence unresolved — a pending event DEFERS expiry (the gateway, sole prune-lane writer, can always drive an accepted intent to a terminal, so the deferral is bounded); on expiry — in the expiry terminal's `TERMINAL_APPLIED` transaction — the reservation releases, admitted checkpoint bytes convert to ordinary charged storage (preemption accounting), and a later cycle starts fresh with no carry. **Immutable terminal evidence — a real CAS (round-12 A2):** EVERY terminal writes exactly ONE service-signed **`maintenance_cycle_terminal`** record at the DETERMINISTIC create-only per-cycle key `maintenance/terminals/<maintenance_cycle_id>.terminal.json` (the terminal CAS — a second byte-distinct terminal cannot land; `object_id` `mct_` rides the body, the admission-record precedent), published through the four-state **terminal machine**: `TERMINAL_PREPARED_NO_IO → TERMINAL_PUT_ISSUED (lane tx: exact signed bytes + frontier persisted; IRREVERSIBLE — every later cycle event refuses from here, not merely once the object is visible) → TERMINAL_STORED (create-only PUT won; identical retry forever) → TERMINAL_APPLIED (ONE idempotent transaction performs the release, handoff, slot transition, and accounting)`. **Composition is exact:** every maintenance/replacement side effect happens ONLY at `TERMINAL_STORED → TERMINAL_APPLIED`; the maintenance machine's terminal STATE means `TERMINAL_APPLIED`, while refusals of later cycle events begin at `TERMINAL_PUT_ISSUED`. **Accepted-event frontier:** the lane assigns a per-cycle monotonic `cycle_event_seq` at each acceptance, signed INTO every cycle-tagged completion; the terminal carries `last_accepted_cycle_event_seq` — after DR, exactly the completions whose signed seq ≤ the frontier count, a stored completion with no signed seq was never accepted, and a late-visible object can never flip the derived terminal. Terminal-kind matrix (schema-enforced): COMPLETED/ABORTED/EXPIRED carry null successor+repair ids; RESTART carries the successor (≠ the predecessor); PREEMPTED carries the repair attempt id; ABORTED has null progress; EXPIRED has non-null progress with `terminal_at ≥ last_cycle_progress_at + 7d`; authority time = `terminal_at`. **ONE exclusivity rule:** an org has at most ONE open maintenance cycle; opening consumes the org slot AND the `(vault, base head)` lease — the lease is the vault-local instrument of the org slot; both release together in that terminal's `TERMINAL_APPLIED` transaction. **No cycle transition is accepted while a repair fence is pending** (`REPAIR_FENCE_PENDING`), and `PREEMPTED_BY_REPAIR` terminalizes only when the repair record provably WON. **Stage-wise reservation (the peak-space invariant):** `M_cycle ≥ max(0, R1 − P_before_C1, R1 + R2_cap − P_before_C2) + 256 MiB`, where **`R1 := admission_source_bytes_charge(C₁)`** and **`R2_cap` := the maximum permitted `admission_source_bytes_charge(C₂)`** under the defined growth envelope, reserved before C₁ admits; `reserved_total_size_bytes` is the INITIAL peak reservation fixed at the C₁ arm. **Each credited `P` is the `p_before_size_bytes` of a stored, service-signed `maintenance_completion_cut` object (round-16 A1, publication closed round-17 A1)** — keyed by ADMISSION ATTEMPT: create-only at `maintenance/cuts/<admission_object_id>.json`, published through the **COMPOSITE ADMISSION FENCE (round-18 A2, made total round-20 A1)**: under the org-slot/cycle lane, EVERY fallible admission check runs FIRST — generation/head linkage, request-to-C₁ equality, expected-stage equality + stage reservation, the cycle/terminal/repair/replacement predicates, cutoff + authorization epoch, the generation/rate reservation, lease + quota — THEN `prepared_at`, the service signature, the EXACT admission-record bytes AND the EXACT cut bytes are fixed, and ONE transaction persists both journals, CLAIMS the cut (`claim_owner` = this admission), reserves the stage, and enters `CUT_PUT_ISSUED` AND `CYCLE_ADMISSION_PENDING` together; **after this transaction no semantic validation may refuse** — the rest is mechanical no-fail replay (`CUT_STORED` precedes `RECORD_PUT_ISSUED`); the record's service signature attests THIS composite validation, and authority time freezes at the admission's irreversible fence (composite for P-credit; `RECORD_PUT_ISSUED` for P-less). The cut's lifecycle row PUBLISHES when the admission COMMITs; **the only unbound-cut exits are `CONFLICTED`** (different-winner proof releases it to the reaper) **and `DR_ORPHANED_PRE_RECORD`** — an unbound cut is inert for P AND fully accounted, carrying the EXACT sorted counted-completion list (`{object_id, stored_bytes_sha256, size_bytes, credited_deleted_size_bytes}`, sorted and UNIQUE by completion id; `credited_deleted_size_bytes` derives exactly from the completion's `deleted` results and their object receipts) plus the total (`p_before_size_bytes` = the exact sum), the binding `admission_object_id` + `admission_generation`, and `cut_at` (its authority time); the admission record binds it via `p_cut_sha256` (null IFF no P is credited — a stored EMPTY cut is prohibited). **A cut whose admission attempt loses (CONFLICTED) is INERT** — DR honors only cuts bound through a canonical record's `p_cut_sha256`, and a retry attempt writes a FRESH cut under its own admission id (the per-attempt key makes CAS loss harmless; the list bound is `MAX_CUT_COMPLETIONS`). DR reads the bound list, recomputes membership and total in LINEAR time, and REFUSES on mismatch; a completion whose PUT was unresolved at the cut is ABSENT from the list and therefore outside it BY CONSTRUCTION — later visibility changes nothing. Each `P` counts ONLY completion-confirmed physical deletions computed under the SAME recovery-bundle protected algebra — no byte of `RB(K₀)`/`RB(K₁)` may enter any `P` while protected. Ordinary growth during a cycle is separately reserved within `R2_cap` or forces a defined cycle restart before acceptance — a writer can never silently strand C₂. **Repair preemption is deterministic**: a repair attempt preempts an open ordinary cycle (→ `PREEMPTED_BY_REPAIR`, reservation released as above); the repair's mandatory checkpoint uses **`checkpoint_purpose:"repair"`** with the repair lane's own reservation — never a cycle id, never ordinary quota (round-7 A1). **Bootstrap** (no current checkpoint) applies ONLY when C₁ replaces already-admitted WAL-backed state — never to brand-new first-capture bytes. Quota escape is guaranteed while the REQUIRED CHECKPOINT COVERAGE (not merely the live reachable set) fits the documented V0 maximum — which the §4.6 invariant keeps true for every admitted vault. One active maintenance lease per (vault, base head); the lease `{maintenance_lease_id, maintenance_cycle_id, base_head_sha256, current_checkpoint_hash, reservation}` is consumed atomically at admission **and recorded in the admission record's `resource_binding`** (§4.10 — DR-reconstructable, round-6 H8); if an ordinary writer advances the head first, the lease invalidates BEFORE any reservation is consumed and compaction rebuilds from the new head. Reservation R = total proposed checkpoint_set bytes; admitted while `org_used + R ≤ org_limit + M`; superseded checkpoint bytes decrement at their prune; an unconsumed lease expires in 7 days and converts to charged storage. The product claim is "compaction is admitted up to the documented maintenance limit — sized so an at-quota vault can complete the reclaim cycle." Advisory at >100 WAL entries or >500 MiB since last checkpoint.

### 7.3 Prune — two-phase, attested, ACYCLIC (round-4 C3), serialized with repair by `gc_epoch`

Every vault has a monotonic **`gc_epoch`**, bumped by every repair admission. Prune intents bind the epoch; a mismatch at any later step refuses with `GC_EPOCH_STALE` — repair and prune can never interleave destructively (round-4 C4).

1. Client computes the delete set (outside the GC root set: the latest usable checkpoint's **RECOVERY BUNDLE** — its claim set + manifest + packs + its covers_through head's `ref_state` and `retention_roots` — + its WAL suffix + the immediately prior checkpoint's recovery bundle + unexpired root carriers + live sessions + claimed/published-pending rows; and past the ≥90-day schedule). **≤ 10 000 candidates per intent** — larger prunes chunk into successive intents.
2. Build **`prune_intent_core`** (owner-signed; NO receipt hashes — the acyclic base): `{repo_id, object_id ("pi_…"), gc_epoch, maintenance_cycle_id|null + maintenance_prune_role|null + stage_claim_set_sha256|null + batch_index|null + batch_count|null (§7.2 — non-null together iff cycle-advancing; the delete set must equal the bound stage's page `batch_index` verbatim), authorizing head hash, checkpoint claim-set hash, gc_root_set_hmac (label "gcrootset", §1 — the sorted complete pruneable receipts), retention-root-state HMAC, sorted delete set (per-candidate EXACT receipt from the CLOSED pruneable union, §4.1; pairwise-distinct, sorted by object_id), nonce}`. **Both `verifier_receipt`s sign `intent_core_sha256`** — each over `{repo_id, intent_core_sha256, checkpoint validity, retention-root evolution validity, per-candidate outside-root attestation, restored-set keyed HMAC, implementation id+version, result}`, signed by the owner's vault key from two separately built implementations — **the V0 implementation identity set is CLOSED: `implementation_id ∈ {"run402-cli", "r402s-verify"}`, schema-enforced; exactly one receipt per identity** (round-9 A3). **Independence is a release-process property, honestly stated** — the receipts defend against bugs, not a malicious owner, who can only harm their own vault.
3. Submit core + receipts to the gateway. ## 9. Control-plane API

### 9.3 Rate limits + the repair resource lane

5000 admitted generations/vault/UTC-day (advisory 1000) + the count caps of §5A. The **repair resource lane** (round-4 H8) is a bounded owner-only reservation covering EVERYTHING a repair needs — upload-session issuance, finalized-object count, temporary storage for the repair checkpoint, the maintenance reservation, and admission — never admission alone; lane objects bind to one repair attempt and are reaped or charged if the repair is not canonized; the lane carries its own tighter abuse limit and audit. ## 14an. Decision log — rev 41 additions (change `gitvault-deploy-lane`)

- **D192** Deploy correspondence is VERIFIED, not isolated (change `gitvault-deploy-lane`, Tal 2026-08-23; supersedes §6.5's "the deploy lane builds from an isolated materialization of the snapshot commit" and the identically-worded client-surface requirement): the client digests the captured file set at capture, re-derives that digest after artifacts are collected and before the apply plan is committed, and on any difference refuses the deploy by name with `SNAPSHOT_MOVED_DURING_DEPLOY` — naming the changed paths, committing no plan. Rationale: the snapshot deliberately EXCLUDES gitignored paths (§6.6 ignore authority), so a materialization of the snapshot commit holds source and NO BUILD OUTPUT, and building inside it requires a build contract the platform has never defined — command, toolchain, dependency fetch, determinism, sandbox, timeout, each its own design. That is why the deploy lane stayed EMPTY rather than half-wired, and why a `required` project was undeployable by every published client: shipping the lane while ignoring the materialization would have produced green deploys that silently voided the guarantee. Verification delivers the property the isolation clause existed to protect — the artifacts correspond to the captured source — without inventing that contract. What is honestly LOST: nothing ties gitignored build outputs to source, so a caller who deliberately ships artifacts built from a different tree is not caught; the guarantee is that the captured source did not change while the artifacts were produced, NOT that the artifacts are a reproducible function of it, and that weaker wording rides the requirement text and the terminal output, never only this log. SCOPE: the claim covers the CAPTURED SET (tracked plus untracked-but-not-ignored) — a build that rewrites ignored outputs between capture and commit is NOT a move, or the feature would be unusable for every project with a build step. REFUSE, NEVER REPAIR: on a detected move the deploy stops and does not re-capture and continue, because a second capture would publish a generation whose relationship to the already-collected artifacts is exactly the thing in doubt, and a capture→collect→capture loop could churn generations indefinitely; the caller re-runs deliberately. `SNAPSHOT_MOVED_DURING_DEPLOY` is CLIENT-LOCAL and deliberately NOT in the §11 registry — the client detects the moved tree before any plan is committed, so the code never crosses the wire, and registering a purely client-side condition would register something nothing can ever emit over it; the accepted cost is discoverability, so it MUST be documented in the client's own error surface rather than assumed findable. The stronger property — artifacts provably a FUNCTION of the snapshot — is carried as a forward TODO with its open questions (what declares the build, which toolchain and who installs it, whether dependency fetching is permitted and how it is bounded, what determinism is claimed and how it is checked, client-side or platform-side) at `openspec/ideas/gitvault-build-from-materialization.md`, and stays unbuilt until they are answered.

## 14ak. Decision log — rev 38 additions (round-38 fold, task 0.73)

- **D186** Heads-listing request/response contract (round-38 finding 1; completes D184): the request is `GET /gitvault/v1/vaults/:vault_id/heads?after_generation=<required verification anchor>&cursor=<optional opaque continuation>&limit=<page size ≤ MAX_HEADS_PER_LISTING_PAGE>` (`heads_listing_request.json`) and the ONE frozen response shape is `{format, repo_id, after_generation, heads[], has_more, next_cursor, total}` (`heads_listing_page.json`, `additionalProperties: false`).
